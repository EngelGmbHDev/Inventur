Inventur

Kurzbeschreibung

Inventur ist die interne Anwendung zur Bestandsaufnahme der privaten Smartphones der Mitarbeiter. Die Arbeit wird in nummerierte Aufgaben unterteilt; jede Aufgabe kann immer nur von einer Person gleichzeitig bearbeitet werden. Es gibt zwei Rollen: Verwaltung (importiert Daten, gibt den Durchgang frei/sperrt ihn, exportiert das Ergebnis) und Mitarbeiter (übernimmt eine Aufgabe und zählt die Artikel je Lagerplatz).

Dieselbe Fachlogik läuft unverändert auf zwei Plattformen: produktiv auf Cloudflare Workers, alternativ als abhängigkeitsfreier Node-Server für einen eigenen Host.

Benutzerhandbuch

Anmeldung

Auf der Startseite entweder „Verwaltung" wählen (ein gemeinsamer Code für die Leitung) oder den eigenen Namen aus der Liste — jeder Mitarbeiter hat einen persönlichen Zugangscode, den er vor Beginn von der Leitung erhält.

Ablauf für die Verwaltung

  1. Anmelden → falls noch Daten vom letzten Durchgang vorliegen: „Durchgang leeren".
  2. CSV mit den Lagerplätzen (lagerplatz;itemcode;aufgabe_num) und die Mitarbeiterliste (name;pincode) einfügen oder als Datei hochladen → „Laden und prüfen". Jeder Mitarbeiter bekommt hier seinen eigenen Code (mindestens 4 Zeichen). Geprüft werden doppelte Lagerplatz/Artikel-Paare sowie Lagerplätze, die versehentlich in zwei Aufgaben auftauchen.
  3. Anzahl Aufgaben und Zeilen gegen die Quelle abgleichen.
  4. „Freigeben" — erst danach sind die Aufgaben auf den Telefonen der Mitarbeiter sichtbar und können übernommen werden.
  5. Über „Aufgabenliste anzeigen" lässt sich jederzeit einsehen, wer woran arbeitet und wie weit jede Aufgabe ist; einzelne Aufgaben können hier bei Bedarf zurückgesetzt werden (z. B. wenn jemand eine Aufgabe halb bearbeitet liegen lässt).
  6. Zum Schluss „Sperren", danach „CSV herunterladen" für das Ergebnis.

Ablauf für Mitarbeiter

  1. Namen aus der Liste wählen.
  2. Persönlichen Zugangscode eingeben — den gibt es von der Leitung.
  3. Eine freie Aufgabe antippen — sie gehört danach nur diesem Mitarbeiter, niemand anderes kann sie gleichzeitig bearbeiten.
  4. Pro Lagerplatz die gezählte Menge eintragen.
  5. Liegt ein anderer Artikel dort als erwartet? Auf die Artikelnummer tippen (Stift-Symbol ✎) und die richtige Nummer eintragen. Die ursprünglich erwartete Nummer bleibt im Export als „Soll"-Wert erhalten.
  6. Liegt zusätzlich noch etwas an dem Platz? Ganz unten in der Liste „Zusätzlicher Artikel am Platz" nutzen.
  7. Alles erfasst? Unten auf „Abgeben" tippen.

Farben am linken Rand jeder Zeile

FarbeBedeutung
Graunoch nicht gezählt
Gelberfasst, aber noch nicht zum Server übertragen (z. B. kein Netz)
Grüngespeichert

Ohne Netzverbindung bleibt eine Zeile gelb und die Übertragung wird automatisch alle 15 Sekunden erneut versucht — nichts geht verloren, es muss nichts neu eingegeben werden. „Abgeben" lässt sich erst antippen, wenn keine Zeile mehr offen ist.

Sonderfälle

  • Aus Versehen die falsche Aufgabe geöffnet? Unten auf „Aufgabe verlassen" tippen — sie wird wieder freigegeben, alle bisher für diese Aufgabe erfassten Werte werden dabei gelöscht.
  • Gerät wird mit Kolleginnen/Kollegen geteilt? Nach der eigenen Zählung bitte oben rechts auf „Ausloggen" tippen, bevor die/der Nächste startet.
  • Fragen oder Probleme? Bitte an die Leitung wenden.

Eine kurze Version dieser Anleitung ist auch direkt in der App über „Anleitung anzeigen" auf der Anmeldeseite abrufbar, sowie als druckbares Blatt in docs/anleitung-mitarbeiter.md zum Aushängen neben dem QR-Code.

IT-Handbuch

Architektur

Die Fachlogik (Anmeldung, Aufgabenvergabe, CSV-Import, Export) liegt vollständig in src/handlers.js und ist plattformunabhängig — sie referenziert keine Cloudflare-spezifischen Objekte. Zwei dünne Adapter binden dieselbe Logik an unterschiedliche Laufzeitumgebungen:

PfadZweck
public/Statisches Frontend (Vanilla JS, kein Build-Schritt), auf beiden Plattformen unverändert ausgeliefert
src/handlers.jsAlle Fachregeln: Login, Aufgabenvergabe, CSV-Import, Export
src/auth.jsPBKDF2 (PIN-Hashing) + HMAC (Bearer-Token) über WebCrypto
src/repo/d1.jsDatenzugriff für Cloudflare D1 (asynchron, gebündelt)
src/repo/sqlite.jsDatenzugriff für node:sqlite (synchron, echte Transaktionen)
worker/index.jsAdapter Cloudflare Workers (~35 Zeilen): routet /api/*, alles andere über die ASSETS-Bindung
server/index.jsAdapter Node: node:http + node:sqlite, ohne npm-Abhängigkeiten
schema.sqlAlleinige Quelle für das Datenbankschema (SQLite-Dialekt, von beiden Adaptern genutzt)

Wichtig für Änderungen: Ein Schema-Update in schema.sql muss identisch in src/repo/d1.js und src/repo/sqlite.js nachgezogen werden — das sind zwei unabhängige Kopien desselben SQL.

Eigener Server (Self-Hosting)

Voraussetzung: Node ≥ 24 (oder Node 22 mit --experimental-sqlite).

openssl rand -hex 32                      # → TOKEN_SECRET
node server/setpin.js admin ACHTSTELLIG   # Code für die Verwaltung setzen (mind. 8 Zeichen)
TOKEN_SECRET=... node server/index.js     # → http://localhost:8080

Mit Docker:

docker compose up -d
docker compose exec inventur node server/setpin.js admin ...

Vor dem ersten Start die Domain in compose.yaml an das eigene Traefik-Setup anpassen (aktuell als Platzhalter: inventur.example.de).

Cloudflare Workers (Produktivbetrieb)

Ein Worker liefert sowohl die Statik aus public/ (Asset-Bindung) als auch die API unter /api/* aus. Reihenfolge beim Erstaufbau: erst die D1-Datenbank anlegen, das Schema anwenden, dann deployen. 

wrangler d1 create inventur          # id → in wrangler.toml eintragen
wrangler d1 execute inventur --remote --file=schema.sql
wrangler deploy
wrangler secret put TOKEN_SECRET     # openssl rand -hex 32

wrangler d1 execute inventur --remote --command="$(node server/pinsql.js admin Sommer2026)"

Wichtig: Ein einfaches git push löst kein Deployment aus — es ist keine Workers-Builds/Git-Anbindung für dieses Repository eingerichtet. Produktiv wird nur aktualisiert, wenn jemand manuell wrangler deploy ausführt. Ebenso wenden weder schema.sql noch die Secrets sich automatisch an — das sind separate, einmalige, manuelle Schritte gegen die produktive D1-Datenbank bzw. den Account.

Die database_id in wrangler.toml muss zu einer tatsächlich existierenden D1-Datenbank passen (wrangler d1 list) — eine veraltete oder falsche ID lässt den Worker für jede Anfrage mit Cloudflare-Fehler 1101 fehlschlagen, noch bevor die eigentliche Anwendungslogik greift, und taucht auch nicht in wrangler tail auf.

Admin-Code zurücksetzen (z. B. bei Verlust)

Geht ohne Login, direkt gegen die produktive Datenbank — praktisch bei Aussperrung:

wrangler d1 execute inventur --remote --command="$(node server/pinsql.js admin NeuerCode123)"

Für den eigenen Server stattdessen:

node server/setpin.js admin NeuerCode123

Sonstiges

  • Es gibt keine Test-Suite, keinen Linter und keine CI-Pipeline in diesem Repository.
  • RUN = 1 in src/handlers.js ist aktuell ein fest verdrahteter, einzelner aktiver Durchgang; run_id ist zwar bereits durchs Schema und die Datenzugriffs-Schicht durchgereicht, wird aber noch nicht für mehrere parallele Durchgänge genutzt.
